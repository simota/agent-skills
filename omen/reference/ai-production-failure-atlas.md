# AI Production Failure Atlas

**Purpose:** A pre-built catalog of 22 failure modes specific to AI-assisted production pipelines (design, content, code, research). Use it to seed the IMAGINE / ENUMERATE phases when the analysis scope involves generative tooling, so the catalog doesn't have to be re-derived from scratch each time.
**Read when:** the plan under pre-mortem includes an AI-generation step — image/copy/code/UI generation, AI-assisted research, or an agent with write access — and you need a starting failure-mode list instead of blank-page brainstorming.

**Source:** adapted from *AI-era design production* literature (Appendix B, "Failure Atlas") and re-cut for pre-mortem use — each entry here answers "how would I detect this before it ships," not "how do I avoid it in general."

---

## Operational principle: diagnose the layer before regenerating

**Do not respond to a symptom by asking for "a better prompt."** Every failure mode below traces to exactly one of five layers. Identify the layer before proposing a fix — a Context-layer failure fixed with a Workflow patch (or vice versa) recurs, because the fix didn't touch the mechanism that produced it.

| Layer | Question it answers | Typical fix class |
|-------|---------------------|--------------------|
| **Context** | Was the task/constraints/evaluation criteria actually specified, or compressed into one instruction? | Re-separate intent / axes / gates; supply missing reference or ground truth |
| **Workflow** | Does the production pipeline enforce structure (states, components, registries) or does it end at "looks done"? | Add a pipeline stage, checklist, or connect to an existing registry/contract |
| **Evaluation** | Is review capacity matched to candidate volume, and are mechanical checks used where they exist? | Bound batch size, reclassify Gate vs. lens, insert automated check |
| **System** | Does this failure only appear when local automations compound across the whole pipeline? | Systems-level integration review, not a point fix |
| **Governance** | Is this about rights, disclosure, permission scope, or who is accountable for the output? | Policy control, not a prompting or tooling fix |

**Rule:** hold the ENUMERATE phase open until the layer is identified. A failure mode logged without a layer tag is not yet actionable — see `omen/SKILL.md` Core Contract (RPN/AP scoring still applies per-mode; the layer tag is a prerequisite to choosing *which* mitigation class to score).

## Catalog

Severity/Occurrence/Detection are not pre-scored here — score them against the actual system per `reference/scoring-methodology.md`. The **Detail** pointer routes to the file with the fuller mechanism/mitigation writeup where one already exists, to avoid duplicating that content.

| ID | Failure Mode | Layer | Symptom | Mechanism | Detection | Detail |
|----|-------------|-------|---------|-----------|-----------|--------|
| F-01 | Prompt Fixation | Context | Output stays anchored to the first draft; only wording is edited across rounds | Task, context, and evaluation criteria were compressed into one instruction, and the failure gets misdiagnosed as a vocabulary problem in the prompt | Re-read the last 3 revisions: if only adjectives/wording changed and structure didn't, fixation is active | `_common/CANDIDATE_SELECTION.md` §9 (`prompt fixation`) |
| F-02 | Reference Copying | Workflow | Output's composition/motif is recognizably close to one specific existing work | A single reference was passed through at full fidelity as a finished exemplar, with no counter-reference | Independent similarity look by someone who hasn't seen the reference; side-by-side placement | `_common/ASSET_PROVENANCE.md` §8 (`reference copying`), §5 (three-column reference discipline) |
| F-03 | Over-generation | Evaluation | Candidate pile diverges; no one can hold the batch in mind; near-duplicates accumulate | Cheap generation externalizes evaluation cost to the reviewer, with no stop condition declared up front | Count near-duplicates vs. axis coverage; batch size and stop condition were never stated before generation began | `_common/CANDIDATE_SELECTION.md` §9 (`over-generation`), §2 (stop conditions) |
| F-04 | Generic Aesthetics | Context | Output is polished but has no case-specific identity; converges to a recognizable "AI-generic" type | Adjective-heavy instructions pull toward the highest-frequency pattern in the training distribution | Compare against 2-3 unrelated outputs from the same tool/prompt family — indistinguishable output is the signal | `_common/CANDIDATE_SELECTION.md` §9 (`surface-only exploration`) |
| F-05 | Style/Brand Drift | Workflow | Tone/visual identity diverges across media, sessions, or operators | No shared Visual Grammar / token system constrains the model; per-session variance dominates | Cross-artifact diff against the design-token/voice baseline; flag deltas outside declared range | `muse` (design tokens), `vision` (Visual Grammar ownership) |
| F-06 | False User Insight | Context | An AI-synthesized persona or "finding" gets cited as research | The model fills a data gap with a generic pattern and produces a plausible-sounding causal story | Trace every quoted insight to a source: interview transcript, ticket, or session log — no traceable source is disqualifying | `field` (research design), `_common/EVIDENCE_LADDER.md` (E0 unverified claim) |
| F-07 | Hallucinated Research/Citation | Context | A citation, statistic, or paper reads as real and fluent but doesn't resolve to a source | Retrieval and generation are blended without a hard boundary between "found" and "produced" | Attempt to independently resolve every citation/number before it ships; unresolved = block | `_common/EVIDENCE_LADDER.md` |
| F-08 | Broken Typography | Workflow | Text embedded in generated images is misspelled, overflows, or mangles non-Latin scripts | Image generators treat in-image text as pixels, not as an editable text object | Render at target locale/length and read every character; check overflow at min/max string length | — |
| F-09 | Broken UI States | Workflow | Happy-path screen looks great; Loading / Error / Empty / Permission-denied states are missing or unstyled | Generation converges on the single most common "finished screen" pattern and omits state transitions | Explicitly request and review each state as a separate artifact, not a variant of the happy path | `forge`, `vitrine` (state coverage in the component catalog) |
| F-10 | Accessibility Regression | Workflow | Visual polish improves while contrast, focus order, or keyboard operability gets worse | Semantic structure (headings, landmarks, focus order) is not preserved by image/UI generation, and automated visual QA doesn't check it | Run a mechanical a11y check (contrast computation, keyboard trace) — do not accept a model's self-assessment of AA compliance | `_common/CANDIDATE_SELECTION.md` §4 (Gate must be mechanically checked, not asserted); `canon` |
| F-11 | Inconsistent Components | Workflow | Near-identical Button/Card variants proliferate with slightly different specs | Review happens against a screenshot, not against the component registry or design-token contract | Diff new component props/tokens against the existing registry before merge | `muse`, `vitrine` |
| F-12 | Non-reproducible Results | Evaluation | An adopted output can't be reconstructed or explained later | Only the final artifact was kept; no generation log, prompt, seed, or context snapshot was recorded | Attempt to answer "why was this one chosen" from the record alone, without asking the operator | `_common/ASSET_PROVENANCE.md` §8 (`non-reproducible adoption`), §4 (three kinds of reproducibility) |
| F-13 | Unclear Provenance | System | Nobody can say which parts are generated, from what source, or edited by whom | Technical / Source / Rights / Decision provenance layers are collapsed into a single "AI-generated" label | Ask for the four-layer breakdown per asset; a single label instead of four answers is the finding | `_common/ASSET_PROVENANCE.md` §8 (`unclear provenance`), §1 (four layers) |
| F-14 | Confidential Data Leakage | Governance | Prompts, logs, or outputs contain secrets, client data, or PII | Tool/service was selected before data was classified | Check data classification was assigned *before* tool choice, per input, not retroactively | `_common/ASSET_PROVENANCE.md` §8 (`confidential input`); `_common/SECURITY.md`; `cloak` |
| F-15 | Rights Ambiguity | Governance | Record says "commercial use OK" and nothing else; scope, territory, term are unresolved | Vendor summary trusted in place of resolving the license bundle dimension by dimension | Check each of the 9 license dimensions in `ASSET_PROVENANCE.md` §3 individually — any blank field blocks release | `_common/ASSET_PROVENANCE.md` §8 (`rights ambiguity`), §3 (license bundle) |
| F-16 | Automation Bias | Evaluation | An AI score/recommendation is adopted without independent verification; dissent gets overridden | Fluency and speed of the output are used as a proxy for correctness | Check whether the model's ranking and a human critique were recorded separately, and whether disagreements were surfaced | `_common/CANDIDATE_SELECTION.md` §9 (`automation bias`) |
| F-17 | Review Fatigue | Evaluation | Scrutiny drops for later candidates; the first or loudest option wins by default | Reviewer attention is spent on batch volume instead of meaningful difference between candidates | Check batch size against the 3-5 candidate / 1-3 lens bound, and whether the anchor candidate was re-checked after any break | `_common/CANDIDATE_SELECTION.md` §9 (`review fatigue`), §7 (bounding attention) |
| F-18 | Coherence Debt | System | Duplicate variants, brand-guideline drift, and correction chains accumulate over successive cycles | Point automations (single-prompt fixes) run without being connected to the system as a whole, prioritizing generation volume over integration | Track debt across cycles, not within one: does each cycle leave more unresolved drift than it resolves? | — |
| F-19 | Skill Atrophy | Governance | Operators lose the ability to start, explain, or correct work without AI assistance | Foundational practice tasks were automated away along with the routine ones, removing the learning loop itself | Periodic no-AI capability check on a sample task; declining independent completion rate is the signal | — |
| F-20 | Agent Overreach | Governance | An agent performs an incorrect update, duplicate registration, or unapproved publish | Broad permission scope + an underspecified goal + no declared stop condition let a small error compound unattended | Audit the permission scope, goal specificity, and stop condition *before* the run, not after the incident | `_common/OPERATIONAL.md`; `hone` (hook-based gates); `triage` (post-incident, if it already happened) |
| F-21 | Synthetic Media Misrepresentation | Governance | A generated person, result, or endorsement is received as real by the audience | High presentation fidelity implicitly asserts a truth claim the content doesn't back | Check whether synthetic depictions are used for testimonial, credential, or performance claims — that use is a stop, not a trade-off | `_common/ASSET_PROVENANCE.md` §8 (`synthetic misrepresentation`) |
| F-22 | Generated Code Debt | Workflow | A demo works, but ships with unreviewed dependencies, no tests, and constraints the model couldn't have known | The model fills long-term maintainability decisions (dependency choice, test coverage, deprecation path) with plausible-looking defaults it has no basis to make | Run the standard code-review gate (tests, deps, ownership) on generated code exactly as on human-written code — no exemption for "it's a demo" | `judge`, `radar`, `sentinel` |

## Using this atlas in a pre-mortem

1. **SCOPE**: confirm the plan includes an AI-generation or agentic-write step. If not, use Omen's standard `premortem` or `mode` recipe instead.
2. **IMAGINE**: read the Symptom column against the actual plan. Any symptom that's plausible for this system is a candidate failure mode — carry its ID forward.
3. **ENUMERATE**: for each carried-forward ID, tag the Layer (Context/Workflow/Evaluation/System/Governance) before writing the FMEA row. Don't skip straight to a Detection/Mitigation guess.
4. **SCORE**: rate S/O/D against `reference/scoring-methodology.md` as usual. F-14, F-15, F-20, F-21 typically score S ≥ 9 (data/rights/trust exposure) — verify rather than assume.
5. **FORTIFY**: for F-01/03/04/16/17 pull the mitigation detail from `_common/CANDIDATE_SELECTION.md` §9; for F-02/12/13/15/21 pull it from `_common/ASSET_PROVENANCE.md` §8. For the remaining IDs, mitigation is written directly into the FMEA row per the standard Detection/Prevention/Recovery structure.
